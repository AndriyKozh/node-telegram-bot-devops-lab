# Навчальна практика: Makefile + Dockerfile своїми руками

## Правила навчання

Твоя робота — **власноруч написати Makefile та Dockerfile**. Репозиторій не містить їхніх готових версій. Спочатку виконуй команду у терміналі, перевіряй результат і лише після цього перенось її до target у Makefile. Помилки — частина практики: записуй їх і причини виправлення.

## Етап 0. Досліди застосунок

1. Перевір `node --version`, `npm --version` і `git status`.
2. Переглянь `package.json`, знайди `scripts`.
3. Виконай `npm ci`, `npm run check`, `npm test`.
4. Спробуй запуск без токена. Поясни повідомлення про помилку.

**Самоперевірка:** різниця між `npm ci` та `npm install`? Чому тести працюють без токена?

## Етап 1. Makefile: перше правило

1. Створи порожній `Makefile`.
2. Додай target `check` для раніше перевіреної команди `npm run check`.
3. Перевір `make check` та `echo $?`.
4. Додай target `test` для `npm test`.
5. Додай `.PHONY`. Розберися з табуляцією перед командами.

**Самоперевірка:** що таке target, prerequisite, recipe та `.PHONY`?

## Етап 2. Makefile: автоматизація

1. Додай `install`, `start`, `build`, `clean`.
2. `install` відтворювано встановлює залежності.
3. `start` запускає бота з локальним приватним токеном (не друкуй токен).
4. У Node.js `build` не обов’язково компілює JS. Можеш збирати артефакт через `npm pack` або пояснити, чому достатньо `check` + `test`.
5. `clean` прибирає результати збірки без видалення коду або `.env`.
6. Використай `make -n <target>` для dry-run.

**Самоперевірка:** різниця між `:=` та `?=`? Як працюють залежності між targets?

## Етап 3. Dockerfile: контейнеризація

1. Створи `Dockerfile` на базі підтримуваного Node.js-образу (приклад: `node:22-alpine`).
2. Продумай послідовність: base image → workdir → залежності → код → команда запуску.
3. Створи `.dockerignore`: не включай `node_modules`, `.env`, `.git` та артефакти.
4. Виконай `docker build -t node-telegram-lab:local .`.
5. Перевір `docker image inspect`.
6. Запускай бот із токеном лише через `docker run --rm --env-file .env node-telegram-lab:local`.
7. За бажанням оптимізуй Dockerfile та досліди шари через Dive.

**Самоперевірка:** image vs container? Чому секрети не можна класти в образ?

## Етап 4. Make + Docker

1. Додай `IMAGE_TAG`, що можна перевизначити.
2. Додай `image` через звичайний `docker build` для платформи хоста.
3. Додай `docker rmi $(IMAGE_TAG)` до `clean`; продумай поведінку, якщо образ уже видалений.
4. Перевір `make image`, `docker run`, `make clean`.

**Самоперевірка:** як працює `IMAGE_TAG`? Чому кросплатформний build відрізняється від build для хоста?

## Етап 5. Архітектури

1. Перевір `node -p 'process.platform + "/" + process.arch'` і `docker version`.
2. Порівняй `linux/amd64` і `linux/arm64`.
3. Поясни, чому чужа архітектура без емуляції не запускається.
4. Розмежуй macOS/Windows та Linux-контейнери.

## Етап 6. Git і підсумковий захист

1. `git status`, `git diff` — перевір, що зміни тільки твої.
2. Запусти тести й Docker-перевірку.
3. Коміть `Makefile`, `Dockerfile`, `.dockerignore`; секрети не коміть.
4. Push і перевір файли у GitHub.
5. Поясни без підказок призначення кожної інструкції у двох файлах.

## Критерії готовності

- [ ] `npm run check`, `npm test` проходять
- [ ] `make check`, `make test` проходять
- [ ] Docker-образ збирається й запускається
- [ ] `make image`, `make clean` працюють
- [ ] Секретів немає в Git чи образі
- [ ] Можу пояснити кожен target і кожен шар Dockerfile

**Старт:** відкрий `package.json`, знайди команду перевірки синтаксису і перевір її вручну перед створенням Makefile.
